REGISTRATION_EDGE_FINDER_JSON — Find function-pointer registration (DriverEntry / WDF config)

You are analyzing how a callback/handler function becomes reachable from the OS in a Windows
driver. The tool has enumerated DataRefsTo() for the function pointer and extracted nearby

IMPORTANT
- "No direct callers" is NOT a dead end in drivers.
- The goal is to find the *registration point* where the OS framework learns this entrypoint:
  WDM: DriverObject->MajorFunction[], AddDevice, DriverUnload
  KMDF: WdfDriverCreate(EvtDriverDeviceAdd), WdfIoQueueCreate(EvtIoDeviceControl/Read/Write), etc.

{runtime_function_pointers_json}

INDIRECT CALL HANDLING
When a function is called indirectly via a function pointer:
- Check if the call target matches a known function pointer from .data section
- If the pointer value resolves to a known function, set edge_kind to "indirect_call_ptr"
- If it's a function pointer table/array, set edge_kind to "indirect_call_table"  
- If it's a local callback variable passed as parameter, set edge_kind to "local_callback"
- Always prefer resolved targets over unknown pointers

TASK
1) Decide whether each evidence item represents a real registration of the target function.
2) If yes, identify:
   - registration kind (WDM MajorFunction index, KMDF queue callback, KMDF driver config, etc.)
   - the registrant function where this assignment occurs (the function we must climb to)
   - any dispatch selector info (IRP major code, IOCTL code, queue type)
